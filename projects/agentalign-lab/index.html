Flagship project / AgentAlign Lab

Verifier-guided preference learning pipeline for reliable terminal agents.

AgentAlign Lab turns terminal-agent execution traces and deterministic verifier outcomes into inspectable preference data, split-aware evaluations, and a local observability dashboard.

  • AI reliability
  • Terminal agents
  • DPO
  • Observability

Overview

The system treats agent work as an auditable trajectory rather than a chat transcript. A task is specified as structured input, executed in an isolated workspace, judged by deterministic verifiers, and stored with enough evidence to support preference learning and failure analysis.

Core question

Can deterministic verifier feedback improve terminal-agent reliability through DPO?

Current build

60 tasks, 757 scored trajectories, 345 preference pairs, held-out eval, dashboard.

Build Status

60 deterministic tasks 25 / 15 / 10 / 5 / 5 task families 757 scored trajectories 336 + 9 train/validation pairs 6 evaluation metrics 6 dashboard tabs

The implemented loop covers Python bug fixes, data transformation, JSON/config repair, log extraction, and safety-trap tasks. It validates local DPO dataset construction and includes a CUDA handoff bundle for the next real adapter-training run.

Architecture

AgentAlign separates execution, verification, preference construction, and evaluation so each layer can be debugged independently.

Pipeline

  • 01 Task package Typed task input with files, constraints, verifier config, and expected behavior.
  • 02 Sandbox execution Agent actions run inside an isolated workspace with captured stdout and file diffs.
  • 03 Structured trajectory Every action, observation, failure, and recovery attempt becomes trace data.
  • 04 Verifier pass Deterministic checks produce pass/fail signals and evidence for audit.
  • 05 Preference pair Better and worse trajectories become chosen/rejected DPO examples.
  • 06 GPU DPO handoff Qwen2.5-Coder LoRA config and Colab bundle prepare base-vs-adapter eval.

Design Decisions

  • Use deterministic verifiers before model-graded evaluation wherever possible.
  • Store complete trajectories because preference labels without evidence are hard to trust.
  • Separate task schema validation from execution so bad tasks fail early.
  • Keep held-out evaluations isolated from preference-pair generation.
  • Split tasks before trajectory generation so train and final evaluation cannot contaminate each other.
  • Report multiple metrics, not only pass rate: invalid actions, unsafe actions, timeouts, steps, and failure tags.

Failures

  • Thin traces Early traces captured the final verifier result but not enough intermediate context.
  • Schema churn Adding preference data later forced a cleaner separation between task, run, and result.
  • Verifier overfitting risk Agents can optimize visible tests unless hidden or held-out checks are part of the loop.
  • Scripted contrast limit The current baseline/bad-model comparison validates the plumbing, not real model improvement yet.

Lessons Learned

Reliable terminal agents need more than prompting. The system around the model needs schemas, sandboxes, verifiers, traces, and evaluation discipline so behavior can be measured, compared, and improved without relying on anecdotal demos.

Evaluation Philosophy

Evaluation should be treated as infrastructure. Verifier design, trace fidelity, hidden tests, and failure analysis are part of the product surface because they decide what behavior the system learns to prefer.

The minimum credible claim is local and staged: first prove the feedback loop and data plumbing, then run real GPU adapter training, then compare base and tuned behavior on the fixed held-out split. If DPO does not improve pass rate, the fallback signal is still valuable: evaluation infrastructure, trace analysis, verifier quality, and preference dataset audits.
